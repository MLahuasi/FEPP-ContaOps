# Global Balance Sheet — Importación de planes de cuentas

## 1. Creación de las tablas

SQL de referencia para **PostgreSQL**. Una regional puede no tener un archivo de plan de cuentas. Los archivos se registran por separado y las cuentas conservan su historial mediante los estados `active` e `inactive`.

```sql
CREATE TYPE status_type AS ENUM ('active', 'inactive');

CREATE TABLE regionals (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    code VARCHAR(50) NOT NULL,
    name VARCHAR(255) NOT NULL,
    status status_type NOT NULL DEFAULT 'active',
    create_date TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_date TIMESTAMP
);

CREATE TABLE regional_account_plans (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    regional_id BIGINT NOT NULL REFERENCES regionals(id),
    filename VARCHAR(255) NOT NULL,
    status status_type NOT NULL DEFAULT 'active',
    create_date TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_date TIMESTAMP
);

-- Evita que un archivo activo se asocie ambiguamente a distintas regionales.
CREATE UNIQUE INDEX uq_regional_account_plans_active_filename
    ON regional_account_plans (filename)
    WHERE status = 'active';

CREATE TABLE global_balance_sheet (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    regional_id BIGINT NOT NULL,
    accounting_account VARCHAR(100) NOT NULL,
    name VARCHAR(255) NOT NULL,
    level INTEGER NOT NULL,
    parent_account_id BIGINT,
    status status_type NOT NULL DEFAULT 'active',
    created_date TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_date TIMESTAMP,

    FOREIGN KEY (regional_id) REFERENCES regionals(id),
    FOREIGN KEY (parent_account_id) REFERENCES global_balance_sheet(id)
);

CREATE UNIQUE INDEX uq_global_balance_sheet_active_account
    ON global_balance_sheet (regional_id, accounting_account)
    WHERE status = 'active';
```

**Consideraciones:**

- `regionals` contiene solo los datos administrativos de la regional; puede existir sin un plan de cuentas.
- `regional_account_plans` relaciona cada archivo con una regional. Una regional puede tener cero o varios archivos registrados. Solo se consideran los registros `active` para identificar archivos durante la importación.
- El índice de `filename` evita que el mismo nombre de archivo identifique dos planes activos; los nombres deben ser únicos dentro del repositorio.
- `parent_account_id` referencia el identificador de la cuenta padre; es `NULL` para cuentas de nivel 0.
- `global_balance_sheet.update_date` permite registrar cuándo una cuenta pasa a `inactive`.
- El índice único impide que existan **dos cuentas activas con el mismo código en una regional**, pero permite el mismo código en distintas regionales y varias versiones históricas inactivas en una misma regional.

## 2. Flujo de procesamiento

### 2.1. Recorrido del repositorio

1. Abrir el repositorio y comprobar que exista `Plan_Cuentas`. Si no existe, registrar el error y finalizar con el reporte.
2. Buscar el siguiente archivo. Si no hay archivos pendientes, generar el reporte final y terminar.
3. Buscar el archivo por `regional_account_plans.filename` con estado `active`, obtener su `regional_id` y comprobar que la regional exista y esté `active`. Validar que el archivo sea PDF o Excel. Ante un problema, registrar el error y continuar con el siguiente archivo.
4. Iniciar **una transacción por archivo**.
5. Marcar como `inactive` las cuentas actualmente `active` de esa regional y actualizar su `update_date`, **sin eliminarlas**.
6. Procesar el archivo e insertar sus cuentas con estado `active`.
7. Si el archivo finaliza correctamente, confirmar los cambios (`COMMIT`). Si ocurre un error, detener su lectura y revertir **todas las operaciones de ese archivo**, incluida la desactivación de cuentas anteriores (`ROLLBACK`); registrar el error.
8. Regresar al paso 2 para procesar el siguiente archivo, independientemente del resultado del anterior.

### 2.2. Lectura del archivo

1. Leer el PDF **línea por línea** o el Excel **fila por fila**.
2. Identificar si el registro contiene una cuenta contable. Ignorar títulos, encabezados y textos comunes, por ejemplo, `FONDO ECUATORIANO POPULORUM PROGRESSIO`.
3. Si contiene una cuenta, extraer su **código** y **nombre**, calcular el **nivel** y determinar su **cuenta padre**.
4. Validar que la cuenta no esté repetida dentro del plan actual y, si tiene padre, que este ya exista como cuenta `active` de la misma regional **en la importación actual**. Ante cualquier incumplimiento, detener el archivo.
5. Insertar la cuenta como `active` en `global_balance_sheet` y continuar la lectura.
6. Al terminar el archivo, devolver el control al flujo principal para confirmar la transacción y buscar el siguiente.

La identificación, validación y persistencia se realizan durante la lectura; no se requiere una etapa intermedia para procesar todo el documento.

## 3. Reglas de negocio

### 3.1. Regionales

- **RN-01.** Cada archivo se asocia con una regional mediante `regional_account_plans.filename` y `regional_account_plans.regional_id`, considerando únicamente planes `active`.
- **RN-02.** Todas las cuentas del archivo usan el `regional_id` identificado.
- **RN-03.** Una regional puede existir sin un archivo asociado. Si el archivo no tiene una asociación activa válida o la regional está inactiva, se omite su procesamiento y se registra el error.

### 3.2. Cuentas contables

- **RN-04.** Solo se procesan registros que contienen una cuenta contable; los demás se ignoran.
- **RN-05.** El código de una cuenta está formado por números separados por puntos, por ejemplo, `1.1.02.01`. La distribución del código y nombre puede variar entre archivos.
- **RN-06.** Las cuentas principales son:

  | Código | Nombre        |
  | ------ | ------------- |
  | `0.`   | Saldo Inicial |
  | `1.`   | Activo        |
  | `2.`   | Pasivo        |
  | `3.`   | Patrimonio    |
  | `4.`   | Ingresos      |
  | `5.`   | Cobros        |
  | `6.`   | Gastos        |

### 3.3. Niveles y jerarquía

- **RN-07.** Una cuenta cuyo código termina en punto (`.`) puede actuar como padre. Una cuenta puede ser padre e hijo a la vez.
- **RN-08.** El nivel corresponde a la **cantidad de puntos que separan segmentos numéricos (antecesores)**. El punto final, si existe, **no se cuenta**. Por ejemplo, `1.1.1.1.1.01.01` es de **nivel 6**.
- **RN-09.** El código del padre se obtiene quitando el último segmento numérico y manteniendo el punto final. Las cuentas de nivel 0 no tienen padre.
- **RN-10.** Cada cuenta hija debe encontrar su padre previamente insertado como `active` en la misma regional y en la importación actual; de lo contrario, el archivo falla.

| Cuenta            | Nivel | Código padre    |
| ----------------- | ----: | --------------- |
| `1.`              |     0 | Ninguno         |
| `1.1.`            |     1 | `1.`            |
| `1.1.01`          |     2 | `1.1.`          |
| `1.1.02.`         |     2 | `1.1.`          |
| `1.1.02.01`       |     3 | `1.1.02.`       |
| `1.1.1.1.1.01.01` |     6 | `1.1.1.1.1.01.` |

### 3.4. Duplicidad, recargas y estados

- **RN-11.** Una regional no puede tener dos cuentas `active` con el mismo `accounting_account`; si el archivo contiene un código repetido, se considera un error y se interrumpe su procesamiento.
- **RN-12.** El mismo código de cuenta puede existir en **distintas regionales**.
- **RN-13.** Se permiten múltiples importaciones para una regional. Antes de insertar el nuevo plan, las cuentas previamente activas pasan a `inactive` y se actualiza `update_date`. Los registros históricos no se eliminan.
- **RN-14.** Una regional puede conservar varias cuentas históricas `inactive` con el mismo código, pero **como máximo una `active`** para ese código. Las búsquedas operativas de cuentas y padres deben considerar `status = 'active'`.

### 3.5. Integridad y errores

- **RN-15.** Cada archivo se procesa en una transacción independiente. Un error revierte tanto los registros nuevos como los cambios de estado efectuados para ese archivo; los datos anteriores quedan como estaban.
- **RN-16.** Los errores de lectura, validación o almacenamiento detienen solo el archivo afectado. El recorrido continúa con los demás archivos.
- **RN-17.** Todos los errores se acumulan y se presentan al finalizar el recorrido del repositorio.

## 4. Reporte final

El reporte incluye el número de archivos encontrados, correctos y fallidos, y la cantidad de cuentas importadas correctamente. Por cada error registra: **archivo, regional, línea o fila, código contable (si aplica) y motivo**.
